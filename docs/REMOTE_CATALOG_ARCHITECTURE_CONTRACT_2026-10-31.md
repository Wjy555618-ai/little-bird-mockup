# 远程样机库两阶段架构与上线合同

合同 ID：`MOCKUP-REMOTE-CATALOG-CONTRACT-1`  
决定人：Wang Zhentao  
状态：阶段零 Netlify 免费静态目录试运行已授权；GitHub、Figma Community 提交和长期中国大陆生产绑定仍未授权  
适用范围：正式样机目录的托管、更新、故障降级、回滚、监控与供应商迁移。  
机器合同：`quality/remote-catalog-contract.json`

## 1. 当前决定

决定人已把当前主目标改为：**三天内先跑通免费插件的真实线上闭环，付费、团队私有、中国大陆正式域名和备案后移数月。** 因此采用两阶段架构：

- **阶段零：三天线上闭环。** 允许使用一个精确的 `*.netlify.app` HTTPS 来源，手动、无 Git 地部署只读正式样机运行时目录；只用于免费插件试运行，不宣称中国大陆长期生产质量。
- **阶段一：长期生产。** 继续采用供应商无关的静态只读数据平面、项目自有固定 HTTPS 域名和私有控制平面；备案、付费和团队私有在独立合同中完成。

阶段零授权不包含 GitHub 连接、任意 Netlify 通配域、质检台/源码公开、Figma Community 提交、收费、账号或团队私有能力。质检台、创作委托、批准接口、原始参考图、权利材料、构建源码和部署凭据始终不得进入公开目录。

## 2. 为什么采用这一模型

当前本地闭环已经证明：五个 r3 样机可以经过单次委托、技术 QA、一次最终批次决定、不可变复制和原子 manifest 更新进入正式库。插件运行时只需要 manifest、当前活动 revision 的主图和缩略图，不需要质检台、历史 revision、批准文件或服务器计算。阶段零必须先生成严格白名单候选，不能直接公开整个 `catalog/production` 历史目录；这既保留摘要、缓存和失败关闭能力，也避免旧绿幕 revision 和内部路径被公开。

不采用以下方案：

- 把素材打包进插件：每次增加样机都要重新发布插件，违背独立更新目标。
- 把质检台或写接口一起公开：扩大攻击面，并可能暴露参考图、审核记录或写权限。
- 在插件中硬编码供应商域名：更换供应商会迫使插件重新上架；固定自定义域名才能把供应商迁移留在 DNS/源站层。
- 当前直接建设数据库、账号或动态 API：现阶段的上线对象仍是免费公开目录；虽然决定人计划在未来一年内评估付费或团队私有样机，但现在预先建重后端只会增加凭据、隐私和故障面。正确方法是保留独立身份/权利层的扩展边界，商业化前再单独冻结并实现。

## 3. 唯一端到端架构

```text
私有控制平面
参考图/权利记录 → 候选 → 质检台 → 一次最终批准 → 本地 production → 发布候选校验
                                                                    ↓
阶段零公开只读数据平面
精确 Netlify HTTPS origin /v1/manifest.json → 当前活动 revision 主图/缩略图
                                                                    ↓
免费 Figma 插件试运行：固定 origin、GET/HEAD、摘要校验、有效缓存、失败降级

阶段一长期数据平面
项目自有 HTTPS 域名 /v1/manifest.json → 当前活动 revision 主图/缩略图
                                                                    ↓
正式 Figma 插件：供应商可迁移、备案、监控与商业扩展
```

控制平面可以在本机或受控 CI 中执行，但必须使用最小写权限。数据平面不保存密钥，不接受用户上传，不运行远程 JavaScript，不提供 POST/PUT/PATCH/DELETE，不向插件返回动态可执行内容。

## 4. 阶段零临时来源与阶段一域名解耦

- 阶段零可以绑定一个且仅一个实际创建并验证的 `https://<exact-site>.netlify.app` origin；禁止 `*.netlify.app` 通配授权、随机预览 URL、跨 origin 资源和重定向 manifest。
- 阶段零不购买域名、不连接 GitHub、不启用动态函数、数据库、身份或写接口；只手动部署 `dist/netlify-catalog` 白名单候选。
- `dist/netlify-catalog` 只允许包含当前 production manifest、该 manifest 当前活动 revision 的主图/缩略图和 `_headers`；旧 revision、批准文件、质检台、测试库、源码、参考图和凭据一律拒绝。
- 阶段一正式插件只允许访问一个项目控制的自定义 HTTPS 域名，路径固定为 `/v1/manifest.json` 及其相对资源，不再直接依赖 Netlify 域名。
- 从阶段零 Netlify origin 迁移到阶段一自有域名属于插件网络权限变化，必须发布一次插件更新；不得假装素材更新可以完成这次域名迁移。
- 阶段一更换托管供应商时保持自定义域名和路径契约不变，通过 DNS/源站迁移完成。
- schema v5 的兼容更新继续使用 `/v1/`；破坏性 schema、渲染器或权限变化必须使用新的路径版本并先发布兼容插件。

## 5. 远程发布协议

每次素材更新必须按以下顺序执行，不能跳步或交换顺序：

1. 只从已通过本地正式入库的 production 版本创建发布候选；
2. 在隔离目录重新校验 manifest、所有引用文件、SHA-256、批准记录和目录历史；
3. 生成不可变部署快照并记录目录版本、manifest SHA-256 和文件清单；
4. 先上传所有带 revision 的新素材、缩略图及公开所需报告；
5. 逐项验证远程资源返回 200、正确 Content-Type、正确字节数和 SHA-256；
6. 只有资源全部可用后，才以平台原子部署或等价原子指针切换激活新 manifest；
7. 从当前阶段固定的精确 origin 禁止重定向地读取 manifest，确认远程字节与本地正式 manifest 完全相同；
8. 记录供应商部署 ID、域名、目录版本、manifest 摘要、执行人、时间和原始检查结果；
9. 进入受控观察窗；监控失败时执行回滚协议。

同一 `assetId + revision` 的远程路径不可用不同字节覆盖。远程发布失败时旧 manifest 必须继续有效，不允许插件看到半套目录。

## 6. 缓存与运行时降级

- `manifest.json` 必须返回 JSON Content-Type，并使用 `Cache-Control: no-store, max-age=0, must-revalidate`；不得重定向。
- 带 revision 的图片使用 `public, max-age=31536000, immutable`，字节由 manifest SHA-256 再校验。
- 插件只接受构建时固定的同源目录；跨域、跨环境、schema/renderer/最低版本不兼容、未来时间、绝对资源 URL、路径穿越、错误状态或摘要漂移全部拒绝。
- 网络失败或目录超时时，只能使用同一 manifest URL、同一环境且年龄不超过配置上限的最后一次有效缓存，并明确显示离线状态。
- 新 manifest 无效时保留当前内存目录或最后一次有效缓存，不得用无效数据覆盖。
- 单个新素材缺失或摘要错误时，保留当前样机和用户画面状态，不允许半切换。
- 没有有效缓存时显示可行动错误；用户已导入的设计和编辑状态不得被清空。
- 当前离线上限为 168 小时。正式部署前必须单独决定“离线可用性”和“权利撤回/安全撤回时长”的取舍；在决定前不得宣称可以即时撤回已缓存素材。

## 7. 回滚与事故响应

- 每次发布前保留当前远程部署和本地目录快照；回滚命令默认只演练，显式确认后才能写入。
- 回滚不是把版本号倒退，而是把上一已知良好内容重新发布为新的单调 `catalogVersion`。
- 事故必须在 5 分钟内被发现、15 分钟内恢复上一已知良好版本；这两个阈值沿用 `G-150`，在真实远程环境完成故障注入前不得宣称成熟产品。
- 必测事故：损坏 manifest、缺失素材、错误 SHA、超时、供应商不可用、部分上传、错误 Content-Type、意外重定向和 DNS/证书异常。
- 回滚后必须再次验证正式域名 manifest 字节、全部活动素材摘要以及插件在线/离线行为，并保存证据。

## 8. 隐私、安全与权限边界

- 插件不得把 Figma 选区、用户导入文件、导出结果、搜索词或编辑参数发送到目录服务。
- 公开目录只含插件运行所需的已批准样机数据。原始参考图、权利证明、测试库、质检台、工作流状态、创作委托、私有评论和部署凭据保持私有。
- 公开静态目录可以使用 `Access-Control-Allow-Origin: *`，因为它不包含秘密且不使用 Cookie/Authorization；若未来出现账户、付费素材或个性化权限，必须建立新的身份与授权合同，不能把密钥或永久下载令牌塞进插件。
- 写入凭据只存在于私有发布环境，并采用最小权限、可轮换、可撤销的短期或受控凭据；插件运行包内不得包含写密钥。
- 托管日志只能保留运营必需的请求元数据；保留期限、访问角色和地区必须在供应商选择时明确，不得把用户设计内容加入日志。

## 9. 阶段零 Netlify 与阶段一供应商门禁

阶段零选择 Netlify 不是长期供应商结论，而是为了满足三天时限的可逆试运行决定。只允许：Free 计划硬额度、手动无 Git 部署、精确站点 origin、静态白名单目录和真实 Figma 验证。Netlify 账号、站点、部署 ID、固定 URL、候选摘要和时间必须形成证据；免费额度耗尽导致暂停属于已知风险，不能宣称长期 SLA 或中国大陆稳定性。

阶段零的唯一公开候选由 `pnpm netlify:catalog:prepare` 生成到 `dist/netlify-catalog`。直接把 `catalog/production` 整目录拖到 Netlify 属于合同失败，因为该目录包含不活动历史 revision 和控制平面批准记录。

长期生产供应商名称不是架构。只有同时满足以下条件的托管方案才能进入阶段一：

1. 支持项目自有 HTTPS 自定义域名和可验证证书；
2. 能准确设置 manifest 与 revision 素材的不同缓存头和 MIME；
3. 不强制正式 manifest 重定向；
4. 支持原子不可变部署，或能证明等价的“资源先行、manifest 最后原子切换”；
5. 保留可核验部署历史，并能在不覆盖不可变文件的情况下回滚；
6. 可导出全部文件和元数据，不形成供应商锁定；
7. 提供可用性检查和告警接口；
8. 日志、访问权限、凭据轮换和数据保留可配置；
9. 目标地区的可用性、成本上限和流量计费经过决定人确认；
10. 能在隔离试点中通过本合同的故障注入和远程字节一致性测试。

阿里云、腾讯云或其他长期平台仍是待验证候选；阶段零使用 Netlify 不改变阶段一的供应商选择，也不构成中国大陆生产可用性结论。

当前已根据“中国大陆为主、暂无域名、首期按 100 个真实样机规划且初始最多 200 个、绝对月预算不超过 200 元、一年内可能付费/团队私有”完成两家官方资料纸面筛选。主候选是阿里云 OSS + CDN，备选是腾讯云 COS + CDN；证据、费用模型和未通过项见 `docs/REMOTE_CATALOG_PROVIDER_COMPARISON_2026-10-31.md`。这一结论只允许进入人工供应商决定，不授权购买、备案、DNS 修改或部署。

新增规模与成本硬门禁：

- 首期按 100 个正式样机进行容量和运营规划；未经新决定，初始正式库不得超过 200 个；
- 配置中的 500 项上限只用于拒绝异常或超大 manifest，是技术安全上限，不构成 500 个样机的运营授权；
- 域名、存储、CDN、HTTPS、回源、请求和监控合计的正常月费用目标不超过 30 元；达到 50 元必须成本复核；未经新决定的月度运营上限为 80 元；决定人声明的 200 元仅是绝对预算上限，不是自动可花额度；
- 月度 CDN 流量封顶为 100 GB，在 20 GB、50 GB、80 GB 告警；达到 80 GB 后停止非紧急素材发布并复核；
- 提高 100 GB 流量封顶、超过 80 元运营上限或突破 200 个首期样机中的任何一项，都需要 Wang Zhentao 新的明确决定；
- 供应商存在约 10 分钟监控/下发延迟，任何封顶都不得被表述为绝对零超支保证；正式上线前必须用真实账号价格计算器和 7 天隔离试点复算。

## 10. 长期兼容与商业边界

- 只增加或替换兼容 schema v5 的样机：更新远程目录，不更新插件。
- 改变渲染算法、schema、网络域名、权限或最低插件能力：先发布兼容插件，再发布新目录。
- 公开免费目录可以沿用本合同。决定人已明确未来一年内计划评估付费或团队私有样机；该能力不延伸公开 v1 的权限，而是使用独立的身份/权利服务、私有 Bucket 和短时效签名 URL/CDN 鉴权。商业化前必须先设计并冻结身份、订阅、团队、授权、撤权、离线许可和隐私合同，并发布新插件版本。
- 首期运营规模按 100 个样机规划且初始不得超过 200 个；达到业务上限时先评估分类、清单分片、加载性能、运营成本和审核能力，不得因为程序尚能接受 500 项就静默扩大内容规模。
- 素材数量超过 500、单 manifest 超过 2 MiB 或单素材超过 32 MiB 时，必须先改变目录分片与运行时合同，不能直接扩大上限。
