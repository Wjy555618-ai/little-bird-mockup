# 样机内容接缝：根因、全局修复与证据

日期：2026-10-30  
渲染器：2.3.0  
目录规范：schema v4 / `static-screen-v4`

## 客观结论

截图中的亮线/空缝来自两个几何边界被错误地当成同一个边界：

1. `screen.aperture` 是经过拟合的数学物理开口；
2. PNG 原图的绿幕经过抗锯齿、透视采样和压缩后，会在数学开口外继续留下与开口相连的栅格软边。

renderer 2.2.0 只用第 1 个边界裁剪内容，却会把第 2 个边界中的绿幕色清理成深色底。这些被清理但没有被内容覆盖的像素，就是高倍率下看见的线。300% 预览会把 1 个源像素放大为约 3 个屏幕像素，因此原图中很小的偏差会成为肉眼可见的缝。

这不是用户画面比例问题，也不是简单的 CSS 缩放问题。把孔径统一向外放大虽然能遮线，却会再次让内容进入真实边框；逐像素扩张虽然能追随绿幕，却会重新制造锯齿。两者都不是可接受的根治方案。

## 原图测量证据

共享渲染器沿物理开口的四条边逐点向外扫描，只统计与开口连续的绿幕软边。最终批准报告记录如下，顺序均为上、右、下、左：

| 样机 | 实测外延 | 最大值 / 安全上限 | 截断样本 | 开口内部绿幕覆盖率 |
| --- | --- | --- | --- | --- |
| 工作室显示器 | `[0, 0, 2, 1]px` | `2 / 12px` | 0 | 99.89% |
| 岩石手机 | `[3, 0, 1, 0]px` | `3 / 12px` | 0 | 99.99% |
| 支架手机 | `[5, 1, 5, 2]px` | `5 / 12px` | 0 | 99.90% |
| 石墨笔记本 | `[4, 6, 4, 4]px` | `6 / 12px` | 0 | 100% |

数据说明问题确实存在于源图栅格边缘：不同素材、不同方向需要 0–6px 的覆盖，固定写死 1px、2px 或统一放大都不成立。

## 全局修复

渲染链现在分成三个互不混用的层级：

1. **物理孔径**：保留精确四边形和四角曲率，负责机身真实开口与编辑语义。
2. **接缝覆盖层**：按每条边实测连续绿幕外延，取该边全部样本中的最大值，再生成平滑矢量圆角四边形；它只覆盖真实存在的栅格软边，不采用逐像素锯齿轮廓。
3. **隐藏欠压**：内容在遮罩下预留 `underlap`，为覆盖层提供足够像素，但不改变编辑坐标和物理孔径。

渲染器、插件预览、原尺寸导出和素材质检台共用这一套实现。旧的含义混乱字段 `bleed` 已从 v4 数据中删除。

## 以后上传素材的门禁

“以后不再发生”通过拒绝未知状态实现，不靠猜测：

- v4 只接收带可验证绿幕屏幕区域的 `chroma-edge` 素材；
- 自动测量必须得到完整边缘，任何方向到达上限后仍连续都判定为截断并拒绝；
- `maxEdgeExtension` 最高 12px，`underlap` 必须覆盖该上限；
- 截断样本必须为 0，截断率必须为 0，开口内部绿幕覆盖率必须至少 85%；
- 条目、几何、素材或渲染器任一变化，旧批准报告立即失效；
- 没有可靠屏幕证据的普通位图不会被“假装支持”，而是不能进入正式库。

因此能保证的是：**所有被系统接收并发布的样机都必须先证明接缝完整；无法证明的素材会失败关闭。** 这是对任意上传文件唯一诚实且可验证的保证。
