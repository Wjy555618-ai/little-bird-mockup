# 样机生产流水线开发合同

合同 ID：`MOCKUP-ASSET-PIPELINE-1`，合同版本：`7`

状态：生效

机器运行权威：`quality/asset-pipeline-policy.json`

历史 Demo 交付记录：`.spec-to-demo/mockup-asset-pipeline/handoff.json`（仅供审计，不得再作为日常修复的前置批准机）

本文件是供人阅读的合同说明。发生冲突时，必须停止执行并由决定人裁决；不得选择更方便的一份继续。

## 1. 主目标

建立一条本地优先、可恢复、可追溯且将复杂度由系统承担的样机生产流水线：决定人提供新参考图时一次性明确权利与创作委托；之后由代理完成制作、导入、元数据、分类、技术 QA、构建和真实 Figma 验证。只有全部技术门禁通过后，才向决定人展示一个最终审阅批次，并只请求一次“通过并进入本地正式库”或“不通过”决定。

## 2. 完成标准

本阶段只有同时满足以下条件才可称为完成：

1. 任何候选创建前都存在一份不可变的单次人类委托，绑定准确参考图 SHA-256、`assetId`、分类、权利模式和“最多 1 个候选”；委托不可重复消耗。
2. 系统只对上述委托自动生成或核验 `revision`、尺寸、缩略图、标签和全部文件 SHA-256；不得因内部测试、验收缺口或已有权利声明自行创建候选。
3. 所有目录、文件和状态变更可重复执行；失败不得留下可被误认为完整素材的半成品。
4. 测试库结构、渲染、接缝、来源、完整性检查全部通过。
5. 技术 QA 记录绑定准确 `assetId + revision + itemSha256`，且不以人类视觉批准作为前置条件。
6. 人类只在技术 QA 和真实宿主验证后做一次最终批次决定；批次内每项绑定 `assetId + revision + itemSha256 + qaReportSha256`，同时绑定插件构建指纹和批次指纹。
7. 旧 revision、旧摘要、缺失批准或被修改文件均无法提升到正式库。
8. 提升前保存可恢复快照；正式库清单只在全部不可变文件就绪后原子更新。
9. 插件刷新同一目录即可看到新样机，不需要修改插件业务代码。
10. 一个没有旧聊天上下文的新执行者，能够只依据仓库文件识别当前状态、下一动作和阻塞原因。
11. 成功、失败、边界和恢复场景均有当前运行证据；工程验收只能使用隔离夹具或用户已经委托的真实候选，不得为了“跑通闭环”生产用户没有要求的素材。
12. 所有活动样机底图、缩略图、测试图和导出图均为完整样机；制作、schema、渲染器、质检和发布链路均不存在绿幕、色键板或按颜色推断屏幕边界的机制。
13. 当前四个绿幕正式素材与 `workstation-display-three-quarter r1` 完成新 revision 迁移，旧绿幕 revision 从 testing、production、插件与质检台的活动路径撤下，旧批准不能继续流转。

## 3. 角色与不可转让责任

### 决定人

- 对每张要进入制作的参考图明确发起“制作一个候选”的单次委托；仅发送截图或仅声明权利不构成委托。
- 声明参考图权利模式。
- 对已通过技术 QA 和真实宿主回归的最终批次做一次“通过并入库”或“不通过”决定。
- 决定是否进行任何外部部署。

### 执行代理

- 只能在存在当次有效单次委托时创建或修改原创候选；不得将内部测试需求升级为真实素材生产任务。
- 导入素材、生成缩略图、元数据和摘要。
- 执行分类、质检、故障修复和证据采集。
- 在不要求决定人批准内部基线、构建或候选指纹的前提下，先完成全部技术 QA 和真实宿主验证。
- 只有在有效的人类最终批次决定存在时才能提升正式库。
- 不得替人类声明权利、批准视觉或批准正式入库。

### 系统

- 对确定、重复、可检查的规则实行失败即关闭。
- 拒绝过期批准、未知分类、重复 ID、路径越界、摘要漂移和半完成发布。
- 保存状态、历史和恢复信息。

## 4. 唯一状态机

主路径：

`WAITING_FOR_USER_INPUT → REQUEST_AUTHORIZED → REFERENCE_RECORDED → CANDIDATE_READY → TESTING → QA_PASSED → FINAL_APPROVED → PROMOTED`

可见异常状态：

- `NEEDS_RIGHTS_DECISION`
- `NEEDS_REVISION`
- `QA_FAILED`
- `BLOCKED`
- `REJECTED`

规则：

1. 任何状态只能沿政策声明的转换移动。
2. 素材字节、screen geometry、分类或会影响渲染的元数据变化时，旧 QA 和旧 release approval 立即失效。已经提升后若只改变目录 origin 或环境绑定，既有内容批准保持有效，但新构建的真实宿主证据必须重新生成。
3. `PROMOTED` 不等于 `DEPLOYED`；本资产状态机不创建 `DEPLOYED` 状态。远程发布由独立远程目录合同和证据管理，不能写回或伪装成资产生产状态。
4. 失败必须保留原因和下一动作，不能回退成看似未发生的空白状态。
5. `WAITING_FOR_USER_INPUT` 不是待修复错误，而是没有新用户委托时的正常停止状态；系统不得为消除“待办”而自行生产。

## 5. 素材身份与版本

- `assetId` 是稳定机器身份，使用小写 ASCII kebab-case，不用展示名称作身份。
- `revision` 从 1 开始，必须为正整数。
- 同一设备、场景和视角的修正增加 revision。
- 设备、场景或主要视角发生实质变化时创建新 assetId。
- 任何正式批准绑定 `assetId + revision + itemSha256`，缺一不可。
- 文件名必须包含 assetId 和 revision；相同路径不允许出现不同字节。

## 6. 参考图与来源

权利声明与创作委托是两个不同问题：

- 权利声明回答“这张图能怎样使用”。
- 创作委托回答“现在是否要基于这张图制作一个候选”。
- 任何一项缺失都必须失败关闭。既有截图如果已用于其他资产，重用必须获得当次明确复用授权。

允许的参考权利模式：

- `owned`：决定人拥有参考图。
- `authorized`：决定人确认拥有明确使用授权。
- `reference-only`：只用于理解构图或风格，正式素材必须重新创作，不能复用参考图字节。

未声明权利模式或未获得单次创作委托时，系统不能创建候选。委托必须绑定参考摘要、`assetId`、分类、权利模式、决定人、时间和最多一个候选，成功导入后立即消耗，不得复用。

正式样机仍必须标记 `provenance.kind = generated-in-house`，并保留生成说明、参考摘要和权利模式。系统不能判断法律权利，只能阻止没有人类声明的素材继续流转。

## 6.1 零绿幕与完整样机硬规则

本节由 `docs/ASSET_PIPELINE_NO_GREENSCREEN_DECISION_2026-10-31.md` 授权，属于不可移动约束：

- 绝对禁止以绿色或其他色键颜色作为屏幕替换板。
- 候选底图和缩略图在进入视觉审核时就必须是完整、可展示的样机，不得依赖运行时隐藏占位板。
- manifest、schema、渲染器和测试不得包含 `chromaKey`、`chroma-edge` 或按像素颜色识别孔径的兼容路径。
- 唯一允许的合成机制是显式屏幕几何/孔径遮罩、透视映射，以及可选的前景、遮挡和反射层。
- 自然画面中的绿色不是错误；把绿色当作待替换标记才是错误。自动检查与人类完整性审核必须同时通过。
- 已有绿幕 revision 必须创建新 revision 迁移；不得覆盖旧不可变文件，也不得沿用旧视觉、技术 QA 或正式入库批准。
- 完整底图的屏幕展示来源只能是 `neutral-off` 或 `reference-bound`。`neutral-off` 必须通过中性色度门禁；`reference-bound` 必须绑定与 provenance 相同的准确参考摘要。
- 禁止插件、渲染器、迁移脚本或缩略图脚本生成未经决定人提供或批准的默认界面。没有用户画面时只显示完整底图自己的中性关屏状态。
- “不是绿幕”不足以通过 QA；屏幕内容来源、最终孔径外泄漏和烘焙彩色角块必须分别验证。

## 6.2 交互与几何硬规则

- 素材卡片的外层命中区不得改变尺寸、位置、旋转、缩放或命中几何。只允许不接收指针事件的内层视觉节点，在每次真正移入时采样一次 `±1.8°–2.7°` 的轻微旋转，停留期间保持不变，移出归零；悬停不得添加描边、背景、阴影或亮度。唯一实现与门禁见 `docs/CONTENT_LIFECYCLE_HOVER_ROOT_CAUSE_2026-10-31.md`。
- 裁切的左/右边只能改变水平方向并固定上下边与对边；上/下边只能改变垂直方向并固定左右边与对边；四角才允许双轴缩放。
- 鼠标、键盘、预览、导出和最终像素必须调用同一套几何约束，不得各自维护平行算法。
- 裁切框、设备物理孔径和外层画布是三种不同职责；不得互相复用固定圆角或叠加第二套视觉边界。
- 任一真实宿主回归出现后，旧通过计数和旧构建立即失效，必须在当前构建中复测对应不变量。

## 7. 自动命名与分类

- 分类只允许来自 `quality/asset-pipeline-policy.json` 的受控 taxonomy。
- AI 可以建议分类和标签，但机器必须检查其属于允许集合。
- 不能可靠映射时进入 `BLOCKED` 或 `NEEDS_CLASSIFICATION`；不得创建近义分类。
- 展示名称不决定身份，允许在不改变 assetId 的情况下改进文案。
- 自动生成 ID 后必须进行重复检测；发生冲突时增加语义区分，不用随机覆盖已有素材。

## 8. 技术 QA 与单次最终决定

### 技术 QA

必须验证目录规范、渲染器、尺寸、推荐比例、几何、可见孔径、接缝、来源、文件完整性、四种测试图和人工视检查项。技术 QA 报告由执行系统先生成，不需要决定人先批准候选或内部指纹。

### 最终批次决定

必须在技术 QA 和真实宿主证据就绪后，由确定的人类决定人对整个最终批次作出一次决定，并记录：

- 决定人身份声明；
- 角色；
- 决定时间和时区；
- 批次指纹与插件构建指纹；
- 批次内每个 `assetId`、`revision`、`itemSha256` 与 `qaReportSha256`；
- `approved` 或 `rejected`；
- 对应技术 QA 报告摘要。

本地决定是可追溯的人类声明，不是密码学身份认证。批次内仍然逐项强绑定，但不得因此要求决定人分别复制或批准多个指纹。

## 9. 正式库提升

提升必须按以下顺序：

1. 重算测试项、QA 报告、插件构建和最终批次摘要。
2. 验证批次内每项都绑定同一 assetId、revision、itemSha256 和 qaReportSha256，且批次指纹与决定一致。
3. 保存正式库当前快照。
4. 复制所有不可变素材和批准记录；相同路径不同字节立即失败。
5. 校验目标文件摘要。
6. 最后原子替换正式 manifest，并递增 catalogVersion。
7. 运行正式库检查。

任一步失败时，旧正式 manifest 必须保持可用。

## 10. 新对话和跨电脑连续性

仓库必须提供：

- 根级 `AGENTS.md`：入口、禁区、必读文件、停止规则。
- `docs/ASSET_PIPELINE_RUNBOOK.md`：人类可读操作和恢复流程。
- `quality/asset-pipeline-policy.json`：机器政策。
- 工作队列/状态文件：每个资产的当前状态、摘要、阻塞原因和下一动作。
- 确定性命令：创建、检查、状态、批准、提升和恢复。

新执行者必须先验证合同和当前摘要，再继续；不得从聊天文字推断批准。

## 11. 本阶段范围

### 必须实现

- 本地参考记录和素材导入。
- 不可变的单次人类创作委托、截图摘要绑定、重用授权和消耗记录。
- 自动 ID/revision/尺寸/缩略图/摘要/受控分类。
- 明确工作状态和失败恢复。
- 现有质检台与新状态、双重批准的集成。
- 正式库提升对 release approval 的强制校验。
- 机器合同校验和成功/失败/恢复测试。
- 新对话运行手册。
- 零绿幕 schema/renderer 迁移、全部活动素材 revision 迁移、色键回退代码删除和完整样机门禁。

### 明确不做

- 内置第三方图片生成模型或保存模型密钥。
- 由资产流水线直接授权 GitHub、Netlify、Figma 社区或其他外部发布。精确 Netlify 阶段零试运行只能由独立远程目录合同授权和验收。
- 公网登录、多人权限或云对象存储。
- 声称现有临时素材为最终内容。
- 用模拟通过替代真实本地执行。

## 12. 变更规则

目标、角色、批准语义、状态机、正式库边界或硬门禁发生变化时，必须：

1. 更新机器交付合同并增加 contract_version；
2. 标出受影响的 requirement、task、test 和 evidence；
3. 使对应旧批准失效；
4. 删除或替换失效规则，不能并存两套机制；
5. 若变化影响最终审阅内容，使旧批次决定失效并重新请求一次最终决定；只改变已批准内容的目录 origin 或部署绑定时，不得重新请求内容批准，但必须重新生成该构建的真实宿主证据。普通修复、内部基线和构建指纹不得单独向决定人请求批准。

普通实现进度和重复测试不会改变合同版本。
