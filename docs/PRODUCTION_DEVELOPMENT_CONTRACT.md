# 样机工作室生产级开发合同

合同 ID：`MOCKUP-STUDIO-PRODUCTION-CONTRACT-1`
机器合同：`quality/acceptance-gates.json`
远程目录组件合同：`quality/remote-catalog-contract.json`
适用对象：插件代码、构建配置、远程目录、素材、发布制品、宿主验证和产品成功声明。

## 1. 唯一目标

把样机工作室建设成可重复构建、默认拒绝错误输入、能够在真实 Figma 环境稳定完成核心任务、可回滚且所有成熟度声明都有当前证据支持的产品。

本合同不接受以下替代完成：

- 界面看起来精致；
- 本地构建或若干测试通过；
- 只在一台开发电脑上打开过；
- 演示路径成功但失败路径未测；
- 内部人员表示喜欢；
- 将未执行、跳过、模拟或历史版本证据描述为当前完成。

## 2. 不可变约束

1. 开发、测试和生产环境必须由 `config/plugin.config.json` 这一单一配置源生成。运行时代码和 manifest 不得各自维护第二份地址或版本。
2. 生产构建必须默认拒绝 IP、localhost、保留测试顶级域、`example.com/.net/.org` 及其子域、全零插件 ID、开发权限和未替换令牌；版本标签必须已发布到 origin 且与本地提交一致，构建前后 Git 提交和工作区不得漂移。
3. 正式插件只能接受与构建环境、目录 schema、渲染器版本和最低插件版本完全相容的目录；正式目录只能包含 `approved` 素材。
4. 用户设计内容不得发送到目录服务或其他未声明的远程目标；远程目录只能提供 JSON 和媒体，不得执行远程脚本。
5. 缓存、预取、文件输入、Figma选区导出和历史记录必须有明确上限；素材或选区数量增长不得导致全量高清资源预加载或无界并发导出。
6. 每次正式目录变更前必须保存当前manifest快照；相同revision文件不得被不同字节覆盖；回滚必须恢复旧内容但发布为新的单调版本号，且默认命令只能演练，显式 `--apply` 才能写入。
7. 任何进入插件运行制品的源码、依赖、配置、PDF 运行包、worker、manifest 或构建模板变化都必须改变构建指纹；测试、运营脚本和测量政策必须通过各自的提交、制品摘要或政策摘要独立绑定，不得冒充运行制品指纹的一部分。
8. 真实宿主、跨平台、人工无障碍、性能、回滚和外部用户证据不得由源码字符串测试代替。
9. 不得通过删除测试、降低阈值、扩大超时、跳过场景或改变口径使门禁变绿；阈值改变必须先形成独立决策记录，并使旧证据失效。
10. 当前用户工作区中的既有改动属于用户资产；不得通过重置、覆盖或回退来制造通过结果。
11. “成功产品”必须有真实外部使用和完整留存观察窗，不能由工程完成推导。
12. 远程正式目录必须遵守 `MOCKUP-REMOTE-CATALOG-CONTRACT-1`：项目自有固定 HTTPS 域名、公开只读数据平面、私有控制平面、不可变资源、manifest 最后原子激活和可验证回滚；架构冻结不得解释为供应商选择或部署批准。

## 3. 单一事实源与生成物

| 类型 | 唯一事实源 | 生成物或消费者 |
|---|---|---|
| 插件版本、环境、目录 URL、插件 ID、目录契约 | `config/plugin.config.json` | `plugin/ui.html`、`plugin/manifest.json`、生产制品 |
| 插件 manifest 静态字段 | `plugin/manifest.template.json` | 开发和生产 manifest |
| UI | `plugin/ui.template.html`、`plugin/styles.css`、`plugin/ui.js` | `plugin/ui.html` |
| 渲染算法 | `shared/mockup-renderer.js` | 插件和素材质检台 |
| 目录与素材 | `catalog/<environment>/v1/manifest.json` 及 revision 文件 | 插件运行时 |
| 成熟度门禁 | `quality/acceptance-gates.json` | 合同校验、CI 和发布评审 |
| 远程目录架构与上线门禁 | `quality/remote-catalog-contract.json`、`docs/REMOTE_CATALOG_ARCHITECTURE_CONTRACT_2026-10-31.md` | 供应商评估、远程试点、缓存、故障降级和回滚 |
| 人工测量口径 | `quality/measurement-policy.json` | 证据草稿、证据验真和成功指标算术 |
| CI 与发布保留策略 | `.github/workflows/quality.yml`、`.github/dependabot.yml` | 远程开发门禁、依赖更新和标签制品 |

生成物不得被手工编辑后提交为真相。`pnpm build` 只能生成开发插件；生产制品只能由生产模式在隔离输出目录生成。

## 4. 证据规则

每项通过证据必须同时具备：

- 证据对应的 gate ID；
- 获取时间和责任角色；
- 源提交、发布指纹、目录版本或数据口径绑定；
- 实际输入、执行环境和原始结果；
- 明确的通过条件与失败条件；
- 限制、跳过项和异常；
- 失效条件。

人工证据还必须通过 `scripts/verify-evidence.mjs`：工具直接从正式插件目录读取唯一 `REL-*` 指纹并计算带文件名和长度边界的确定性 SHA-256，从 `v<version>` 标签解析发布源提交，并校验发布包内的 provenance、合同 ID 与合同字节 SHA-256、测量政策 SHA-256、目录版本与目录字节摘要。仅保留相同合同 ID 不足以复用旧证据，合同任一字节变化都会使发布绑定失效。证据必须位于机器合同指定的精确路径；所有必测场景都必须是 `PASS`，且有有效时间、环境、输入、输出、测量值和非空原始附件。每个附件都必须声明路径、字节数和 SHA-256，解析符号链接后的真实路径也必须留在证据目录内。性能、无障碍、回滚和成功指标使用 `quality/measurement-policy.json` 中预先登记的固定阈值；比率必须由安全整数分子/分母重新计算，不能只填写结论值。测量开始时间不得早于政策登记时间，任何政策字节变化都会使旧摘要失效，不能事后降低阈值再复用旧证据。

以下任一情况使证据无效：

- 来自不同发布指纹，却没有证明差异与该门禁无关；
- 只提供截图而没有可识别的输入、版本和输出；
- 只说“已测试”“没问题”或“看起来正确”；
- 用旧版本证据覆盖当前变化；
- 缺少失败场景、分母、时间窗或平台信息；
- 人工修改 JSON 中的通过状态。机器合同刻意不保存 `status`、`passed` 或 `approved` 字段。

## 5. 成熟度声明

### DEVELOPMENT_READY

只能说明当前开发版本满足静态合同、开发构建、自动测试、500项资源上限不变量、本地Chrome 500项目录性能烟测、静态无障碍和依赖审计。不能说明可发布，也不能替代正式REL候选在最低支持Figma设备上的性能预算。

### PUBLISH_READY

必须在 `DEVELOPMENT_READY` 之上，同时通过生产制品、真实 Figma 宿主、Windows/macOS 平台、性能预算、人工无障碍以及隐私/素材权利审查。

### MATURE_PRODUCT

必须在 `PUBLISH_READY` 之上完成真实故障注入、监控和回滚演练。不能只拥有一条理想路径。

### SUCCESSFUL_PRODUCT

必须在 `MATURE_PRODUCT` 之上，拥有外部目标用户的真实任务数据以及预先定义、覆盖完整观察窗的激活、首次成功、无故障会话、重复使用、留存和支持率证据。

任何低等级声明不得包含高等级含义。自动测试全部通过不等于 `PUBLISH_READY`；发布成功不等于 `SUCCESSFUL_PRODUCT`。

## 6. 交付顺序

1. **发布正确性**：单一配置、环境隔离、非占位生产构建、完整指纹。
2. **运行时信任**：环境、schema、渲染器、最低插件版本、素材状态、来源、哈希和质检元数据均默认拒绝不匹配。
3. **规模与恢复**：有界缓存、有限预取、500 项目录、大文件、连续切换、超时和离线恢复。
4. **质量体系**：行为测试、真实像素不变量、宿主 E2E、平台矩阵和 CI。
5. **无障碍与信任**：语义、键盘、读屏、对比度、隐私、素材权利和支持入口。
6. **运营与成功**：故障发现、目录回滚、外部测试和持续指标。

后续阶段不得用来掩盖前序阻断项。每次策略改变必须更新合同或产生绑定当前合同版本的决定记录，并删除被替代的旧机制。

## 7. 变更与例外

本合同没有口头例外。确需变更门禁时必须：

1. 说明原门禁阻止了什么风险；
2. 提供变化证据和替代方案；
3. 证明新门禁不会降低风险覆盖；
4. 更新机器合同、测试和文档；
5. 使旧证据失效并重新验收。

时间紧、演示需要、当前只有一名开发者、某平台暂时不可获得，都不能把失败改写为通过。可以缩小公开支持范围，但必须在产品声明中同步删除未验证能力。

## 8. 当前状态的判定方式

本合同不保存会随源码变化而过期的测试数量、开发指纹或“当前已通过”等人工状态。当前成熟度只能由以下实时证据共同判定：

1. `quality/acceptance-gates.json` 中目标等级的全部门禁；
2. 门禁声明的命令在当前源码、当前锁文件和当前目录上真实执行成功；
3. 人工证据绑定同一个不可变 REL 制品，且仍在有效期内；
4. `release-provenance.json`、Git 标签、远端提交和远程目录摘要一致；
5. 没有未解释失败、跳过项、占位身份、陈旧生成物或未提交漂移。

历史开发指纹、测试计数和真实宿主记录保留在带日期的 QA/证据文件中，只证明各自绑定的版本。没有 `G-020` 与全部 release 门禁证据时，最高只能声明 `DEVELOPMENT_READY`；不得从历史报告推导 `PUBLISH_READY`、`MATURE_PRODUCT` 或 `SUCCESSFUL_PRODUCT`。
