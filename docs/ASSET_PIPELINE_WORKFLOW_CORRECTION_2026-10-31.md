# 样机生产流程根因纠正决定

日期：2026-10-31（Asia/Shanghai）

决定人：Wang Zhentao

## 1. 决定人纠错

> “为什么合同还要求生成候选？我不是在最开始已经给你发了截图了吗？为什么还要生成候选？”

> “现在最严重的问题，是你的工作流程错误，工作流程的错误是你合同等规则的错误，或者是别的什么错误。我要求你彻底找对根因，然后彻底解决这些错误。”

## 2. 可复现事实

1. `docs/ASSET_PIPELINE_DEVELOPMENT_CONTRACT.md` 原完成标准强制“一个全新候选”进入测试库。
2. `.spec-to-demo/mockup-asset-pipeline/handoff.json` 原 `TASK-010` 要求在五个 r2 之外再做一个全新候选闭环。
3. 原 `createCandidate()` 只检查参考权利模式、图片、分类和几何，不要求任何“用户要求创建这一个候选”的独立记录。
4. `limestone-ultrawide-front r1` 因此能仅凭已有截图的 `owned` 权利声明和内部验收任务进入 `CANDIDATE_READY`，却没有当次用户创作委托。
5. 该候选未获视觉批准、未进入技术 QA、未获正式入库批准、未进入 production、未对外发布。五个已批准 r2 正式资产与它相互独立。

## 3. 根因链

### 根因 A：权限语义混同

`owned / authorized / reference-only` 回答的是“参考图可以怎样使用”，却被当成了“用户已经要求再做一个候选”。这两个命题在逻辑上不等价。

### 根因 B：内部验收策略升级为用户交付目标

“用一个全新非迁移候选跑通闭环”本来只是一个工程测试方案，却被写进合同完成标准和 `TASK-010`。它因此变成了必须消除的待办，反向驱动了未经请求的真实素材生产。

### 根因 C：状态机缺失生产前的权威门

原状态机从 `REFERENCE_RECORDED` 开始，没有 `WAITING_FOR_USER_INPUT` 和 `REQUEST_AUTHORIZED`；原导入程序也没有单次、数量受限、可消耗的人类创作委托。所以即使合同文字改对，程序仍无法阻止同类错误。

## 4. 裁决

1. 权利声明与创作委托永久分离。
2. 每个新候选必须先有一份人类委托，绑定准确参考 SHA-256、`assetId`、分类、权利模式、决定人、时间和最多一个候选。
3. 委托只能消耗一次。同一参考图已用于其他资产时，必须有当次明确复用授权。
4. 没有新委托时，流水线的正确状态是 `WAITING_FOR_USER_INPUT`，不得自行消除该状态。
5. 工程端到端测试必须使用临时隔离夹具，或等待下一个真实用户委托；不得为了验收制造真实候选。
6. 原 `TASK-010` 不是未完成的用户任务，必须从当前合同移除。
7. `limestone-ultrawide-front r1` 从活动 testing 路径撤下，标记 `REJECTED`，保留不可变隔离证据，不进入视觉批准、QA 或正式库。
8. 五个已获完整批准的 r2 正式资产保持不变。

## 5. 可验收门禁

- 缺失委托时，候选导入必须在写入任何 manifest、状态或素材前失败。
- 仅有权利声明时必须失败。
- 委托参考摘要、资产身份、分类或权利模式不匹配时必须失败。
- 一份委托生成一个候选后必须立即不可再用。
- 复用已使用的参考图但缺少当次复用授权时必须失败。
- 上述任一失败都不得改变测试清单、正式库和五个已批准 r2。
- 隔离后活动 testing 清单不得再包含 `limestone-ultrawide-front`，隔离文件的 SHA-256 必须与原记录一致。
